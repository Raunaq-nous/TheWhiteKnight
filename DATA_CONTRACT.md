# DATA_CONTRACT.md

> **What this is:** the boundary between files the system can update automatically and files only the user controls. This is the single most important file for protecting your work. Borrowed from career-ops's pattern, customized for CareerOS.
>
> **Where this file lives:** at the root of your repo, alongside CLAUDE.md.

## The two layers

### User Layer

**These files are NEVER auto-updated by Claude, scripts, or skill modes.** Personalization lives here. The user is the source of truth.

```
cv.md                          # canonical CV in markdown
persona/master-cv.md           # the canonical career data
persona/voice-samples.md       # examples of the user's actual writing tone
persona/cover-letters/         # all cover letters ever sent
persona/resumes/               # all tailored resumes
persona/github-projects.md     # synced from GitHub but user-curated
persona/certifications.md      # certs the user has, only user adds
persona/publications.md        # IEEE papers etc.
persona/website-content.md     # snapshot of the user's portfolio site
config/profile.yml             # contact info, location, links
config/target-roles.yml        # the 4-5 buckets and their filters
config/portals.yml             # career page URLs to scan
config/voice-rules.yml         # tone preferences
applications/                  # one folder per job, including all generated artifacts
applications/_archived/        # killed applications, preserved
data/applications-index.tsv    # the master tracker
data/log.md                    # natural-language history written by user
docs/tradeoffs.md              # decisions log, user-written
```

### System Layer

**These files CAN be auto-updated** by skills, scripts, or future system updates. They are versioned, replaceable, regeneratable.

```
CLAUDE.md                      # project memory; user reviews diffs
.claude/skills/*/SKILL.md      # skill definitions
.claude/agents/*.md            # subagent definitions
.claude/settings.json          # hooks configuration
templates/*.html               # PDF templates
templates/states.yml           # canonical status enum
scripts/*.sh                   # helper scripts
scripts/*.mjs                  # update / migration scripts
docs/build-kit/                # the original bootstrap files
docs/spec/                     # PRD, SPEC, REFINEMENT, TASKS — generated by SDD
docs/research/                 # synthesis from research subagents
docs/handoffs/                 # session handoff notes
data/cache/                    # any cached lookups, regeneratable
```

## The protection rules

### Rule 1: Skills cannot write to User Layer paths without explicit user approval

A skill that needs to update something in the User Layer must:
1. Show the user the proposed change
2. Wait for explicit "yes" / "approved" / equivalent
3. Then write

The `tailor-resume` skill writes to `applications/<slug>/resume.md` — that's User Layer (it's an application artifact), so it's allowed because the user invoked the skill.

The `update-status` skill writes to `applications/<slug>/status.yml` — same logic, user invoked, allowed.

A hypothetical `migrate-resumes` skill that wants to rewrite all resumes in `persona/resumes/` — that's a bulk User Layer modification, and it MUST show every diff and get approval.

### Rule 2: Update scripts respect the boundary

When a future version of CareerOS adds new System Layer files (new skills, new templates), the update script:
- Replaces System Layer files unconditionally
- Never touches User Layer files
- Surfaces any conflicts to the user

The reference for this is `update-system.mjs` in career-ops. We'll port the same pattern.

### Rule 3: Hooks enforce the boundary

A `PreToolUse` hook on Write/Edit checks: if the target path is in the User Layer **and** the operation wasn't explicitly approved this session, the hook blocks the write.

This is the deterministic enforcement of Rule 1. The hook script lives at `.claude/hooks/protect-user-layer.sh` (created in Phase 4 implementation).

### Rule 4: Gitignore the right things

System-generated state goes in `.gitignore`:

```
data/cache/
data/applications-index.tsv     # arguable — see below
.claude/local-cache/
*.pdf                           # generated artifacts, regeneratable from .md
output/
reports/
```

**One judgment call:** `data/applications-index.tsv` is a User Layer file (your data) but is regenerable from the `applications/` folder. Decide in Phase 2 whether to commit it (good for backup) or gitignore it (cleaner repo).

## Why this matters

Without the User Layer / System Layer boundary, every system update risks overwriting your hard work. You spent 90 minutes tailoring a resume — a careless skill update wipes it.

With the boundary, you can:
- Pull in CareerOS improvements without losing data
- Forks and copies don't pollute each other's user data
- Multi-profile (v2) works cleanly: each user's persona/ and config/ stay separate
- You can blow away `.claude/` and re-bootstrap without losing applications

This is the discipline that makes the difference between "personal hack project" and "system I trust enough to use daily for years."

## When you're unsure which layer something belongs in

Ask: *"if I deleted this file, can the system regenerate it perfectly?"*

- **Yes** → System Layer (templates, skills, scripts, configs about the system itself)
- **No** → User Layer (your data, your persona, your decisions, your application history)

When in doubt, classify as User Layer. The cost of false-positive (over-protecting a regeneratable file) is low. The cost of false-negative (auto-overwriting irreplaceable data) is high.

## How to extend this contract

When you add a new feature in Phase 4, the spec for that feature MUST include:

1. Which User Layer files it reads
2. Which User Layer files it writes (and how it gets approval)
3. Which System Layer files it adds or modifies

If a feature can't fit this template cleanly, the feature is wrong — split it.
