## 1. Architecture Decisions (from Subagent A: career-ops Reference)

### What to copy verbatim from santifer/career-ops
- **The skill-mode pattern.** career-ops uses 14 specialized modes in a `modes/` directory (we use `.claude/skills/`). Each mode is a focused markdown file with YAML frontmatter. The router pattern (one entry point that classifies and dispatches) is exactly what our `career-os` skill does. Copy this architecture wholesale.
- **The User Layer / System Layer data contract.** career-ops separates `cv.md`, `config/`, `portals.yml` (user-owned, never auto-overwritten) from `modes/`, `templates/`, `scripts/` (system-owned, replaceable). Our `DATA_CONTRACT.md` already mirrors this. Copy the enforcement pattern.
- **The `_shared.md` pattern.** career-ops loads a shared context file alongside every mode. We should create `.claude/skills/_shared.md` with the hard rules (no em dashes, one page, first principles, location mappings) so every skill inherits them without duplication.
- **PDF generation via Headless Chromium.** career-ops uses Puppeteer with HTML/CSS templates. The template-to-PDF pipeline is proven at 740+ applications.
- **The `portals.yml` config for scanner.** A YAML file listing career page URLs with selectors. Simple, extensible, human-editable.

### What to adapt
- **Directory naming.** career-ops uses `modes/` (flat). We use `.claude/skills/<name>/SKILL.md` (nested). The nested structure is better for Claude Code's skill discovery. Keep ours.
- **The Go TUI dashboard.** career-ops ships a Go binary for the status board. We need to decide: Go TUI vs. Next.js web app. See Section 5 below for the tradeoff.
- **Batch processing.** career-ops processes multiple URLs via subagents in parallel. We should adopt this but integrate it with our score-first-then-ask workflow (auto-pipeline in the career-os router).

### What to skip
- **The `_profile.md` customization file.** career-ops puts user archetype preferences in a mode file. We have `config/target-roles.yml` and `config/voice-rules.yml` which is cleaner. Skip _profile.md.
- **The npm/Go toolchain dependency.** career-ops requires Node.js for PDF generation and Go for the dashboard. We should evaluate if we can use a simpler PDF pipeline (e.g., Pandoc + wkhtmltopdf) before committing to Node.js. Decision deferred to Phase 2.

## 2. Tools to Integrate (from Subagent B: Adjacent Tools)

### ApplyPilot (Pickle-Pixel/ApplyPilot)
- **What it does well:** End-to-end 6-stage pipeline (Discover, Enrich, Score, Tailor, Cover Letter, Apply). Playwright MCP for browser automation. Runs locally, data stays private. The scoring step (LLM rates fit 1-10 based on resume) is exactly what our `score-job` skill should do.
- **What it does badly:** Fully autonomous by default; the user has limited control over the submission step. No persistent application tracking beyond the current run. No persona corpus concept.
- **Pattern to borrow:** The Playwright MCP integration for form-filling. ApplyPilot auto-configures Playwright at runtime for worker agents. We should mirror this for our `auto-apply` skill, but always in supervised mode (show the user the filled form before submitting).

### resume-lm (olyaiy/resume-lm)
- **What it does well:** Beautiful Next.js 15 + React 19 + Tailwind CSS UI. Multiple resume templates. AI-powered tailoring. Supabase backend for persistence. Open source with 4k+ stars.
- **What it does badly:** Cloud-first architecture (Supabase, Stripe integration). Not local-first. The data model is resume-centric, not application-centric. No pipeline tracking, no outreach, no status board.
- **Pattern to borrow:** The template system for PDF rendering. resume-lm has well-designed HTML/CSS resume templates that render to PDF via browser. If we build a web UI, the component architecture (React Server Components + streaming) is worth studying.

### JobSync (Gsync/jobsync)
- **What it does well:** Self-hosted Next.js + Shadcn UI. AI resume review, job matching, task logging, analytics. Docker deployment. Data stays private. Built specifically as an application tracker.
- **What it does badly:** Still requires a database (PostgreSQL). The AI features are add-ons rather than core to the workflow. No skill-mode architecture.
- **Pattern to borrow:** The Shadcn UI component library for the tracker dashboard. Clean, accessible, well-tested components. If we go the Next.js route, Shadcn is the right UI layer. Also: the Kanban-style status board for application pipeline visualization.

## 4. Design Language Confirmation (from Subagent D: Teenage Engineering)

### Confirmed correct in docs/build-kit/05-design-tokens.md
- Color palette: off-white background, near-black text, OP-1 orange (#FF6B00) as sole accent. Confirmed against TE product pages.
- Typography: Inter/Space Grotesk for display, JetBrains Mono for data. TE uses proprietary mono fonts but JetBrains Mono is the closest open-source match.
- Spacing: 4px base grid. Confirmed; TE products use strict grid alignment.
- "No shadows, no gradients, no rounded corners" prohibition. Confirmed; TE products use hairline borders exclusively.
- Status pill pattern (uppercase, mono, hairline border). Confirmed against OP-Z display elements.
- Score indicator with Unicode block characters. Novel but consistent with TE's "expose the data" philosophy.

### Gaps or corrections needed
- **Missing: the "knurl" texture.** TE products have a distinctive physical texture (knurled aluminum). In UI, this translates to subtle background patterns on interactive surfaces (e.g., a faint dot-grid on draggable areas). Consider adding as an optional micro-detail.
- **Missing: transition timing.** The doc says "no hover animations longer than 150ms" but doesn't specify the easing function. TE uses linear or ease-out; never elastic/bounce. Add: `transition: 150ms ease-out`.
- **Missing: the orange usage rule specificity.** Orange should appear on: (a) the single primary CTA on any page, (b) the currently active navigation item, (c) progress indicators. Never on backgrounds, never on text, never on more than one element per viewport.
- **Color: accent-success should be verified.** The doc uses #00A86B (jade green). TE products tend to use a slightly cooler green. Minor; keep as-is, it works.

## 5. Key Open Decisions

### Decision 1: UI Platform (Go TUI vs. Next.js Web App)
- **Go TUI (career-ops approach):** Faster to build for a terminal-native user. No dependency on a web server. But: Raunaq is a strategy consultant, not a terminal user. The product brief explicitly asks for a tradeoff analysis.
- **Next.js Web App:** Richer UI, Teenage Engineering design language is better expressed in CSS than ANSI. Shadcn UI gives us production-quality components. But: adds a web server dependency, more complex deployment.
- **RECOMMENDATION:** Next.js. The user is a strategy consultant. The Teenage Engineering design language demands pixel-level control. A TUI cannot express the design tokens faithfully. Start with a local dev server (`npm run dev`); no deployment needed for v1.

### Decision 2: PDF Generation Pipeline
- **Puppeteer (career-ops approach):** Proven, full CSS control, but requires Node.js + Chromium.
- **Pandoc + LaTeX:** Lighter, but limited CSS control; hard to match TE design.
- **Playwright (already needed for auto-apply):** If we're installing Playwright anyway for form-filling, use it for PDF too. One dependency instead of two.
- **RECOMMENDATION:** Playwright for both PDF generation and auto-apply. Single browser automation dependency.

### Decision 3: Data Persistence
- **Markdown + YAML on disk (current plan):** Simple, portable, AI-native. Works for v1.
- **SQLite (career-ops considered this):** Better for querying when application count grows.
- **RECOMMENDATION:** Start with markdown + YAML as planned. Add SQLite index only when querying becomes slow (product brief says ~500 applications). The migration path is known and documented.
